# alerts/ — Prometheus alert rules for a Post Fiat node

16 alert rules for the metrics of [`../exporter`](../exporter/), promtool unit tests (one firing and one
non-firing case per alert), and `run-stack.sh`, which runs Prometheus + Alertmanager + a small
webhook→ntfy bridge in Docker with **every listener on 127.0.0.1** (no ports are opened to the network).

| File | Purpose |
|---|---|
| `postfiat.rules.yml` | Alert rules (severity label, `for:` duration, `summary`/`description`/`runbook_url` annotations) |
| `tests.yml` | `promtool test rules` unit tests, generated by `gen_tests.py` |
| `gen_tests.py` | Hand-written input series + eval times per alert; copies annotations from the rules file |
| `prometheus.yml` / `alertmanager.yml` | Configs used by `run-stack.sh` (15s scrape/eval, inhibit rules, webhook with `send_resolved`) |
| `ntfy_bridge.py` | Alertmanager webhook receiver: logs every firing/resolved alert, forwards to ntfy if `NTFY_URL` is set |
| `run-stack.sh` | `up` / `down` / `status` / `check` (shellcheck-clean) |
| `drill.sh` | Live drill: stops postfiatd, records pending → firing → resolved via both APIs, always restarts the node (trap) |

## Requirements

- The exporter from `../exporter` running on `127.0.0.1:9877`, at the version that exports
  `pft_load_factor`, `pft_close_time_offset_seconds`, `pft_uptime_seconds`, `pft_complete_ledgers_ranges`,
  `pft_validator_configured` and `pft_disk_*` (re-copy `pft_exporter.py` to `/opt/pft-exporter/` and restart it).
- Docker, `curl`, `jq`, `ss`. Images are pinned: `prom/prometheus:v3.5.0`, `prom/alertmanager:v0.28.1`,
  `python:3.12-alpine` (override with `PROM_IMAGE`, `AM_IMAGE`, `PY_IMAGE`).

## Usage

```bash
cd alerts
DOCKER="sudo docker" ./run-stack.sh check     # promtool check/test rules, promtool check config, amtool check-config
DOCKER="sudo docker" ./run-stack.sh up        # validates, starts, then fails if any stack port is not loopback-only
DOCKER="sudo docker" ./run-stack.sh status    # target health, Prometheus pending/firing, Alertmanager alerts
DOCKER="sudo docker" ./run-stack.sh down

# Optional phone delivery through ntfy:
install -m 600 /dev/null ~/.pft-ntfy.env && echo 'NTFY_URL=https://ntfy.sh/<your-topic>' > ~/.pft-ntfy.env
NTFY_ENV_FILE=~/.pft-ntfy.env DOCKER="sudo docker" ./run-stack.sh up
```

`run-stack.sh` mounts the ntfy file read-only into the bridge (`NTFY_URL_FILE=/run/secrets/ntfy.env`) and runs the
bridge as the file's owner. It does not pass the URL as an environment variable, so the topic doesn't show up in
`docker inspect`. The file must be mode 600 or 400 and owned by a non-root user. This was found by
[`secrets/`](../secrets/README.md).

Ports, all bound to 127.0.0.1 with `--network host`: Prometheus 9090, Alertmanager 9093 (the cluster port 9094 is
disabled with `--cluster.listen-address=`), and the bridge on 9095. To reach the UIs from your workstation, use
`ssh -L 9090:127.0.0.1:9090 -L 9093:127.0.0.1:9093 <node>`. Don't publish these ports.

Containers run with `--cap-drop ALL` and `no-new-privileges`, and the bridge runs read-only as `nobody`.
Prometheus keeps 15 days of data in the `pft-prometheus-data` volume, which survives `down`.

Inhibit rules: while `PFTNodeRPCDown` fires, Alertmanager suppresses `PFTNodeNotFull`, `PFTValidatedLedger*` and
`PFTValidatorNotProposing` for the same instance, so you get one alert for the outage instead of four.
`PFTDiskSpaceCritical` suppresses `PFTDiskSpaceLow`.

## Alerts: thresholds, rationale, operator response

Each `runbook_url` annotation links to the matching heading below.

### PFTExporterDown
`up{job="postfiat"} == 0` for 2m · **critical**. Prometheus can't scrape the exporter, so every other alert goes
blind. 2m covers one or two missed scrapes during an exporter restart.
**Response:** `systemctl status pft-exporter`, `journalctl -u pft-exporter -n 50`, then
`curl -s 127.0.0.1:9877/metrics | head`.

### PFTNodeRPCDown
`pft_up == 0` for 1m · **critical**. The exporter answers, but `server_info` on the admin RPC fails: the container
is stopped, crashed, or still starting. 1m rides out a single slow RPC call (5s exporter timeout).
**Response:** `sudo docker ps -a | grep postfiatd`, `sudo docker logs --tail 100 postfiatd`, then
`cd /opt/postfiatd && sudo docker compose up -d`, and finally `sudo postfiat-health` until `server_state: full`.

### PFTNodeNotFull
`server_state < full` (index 4) for 5m · **warning**. A restarted node needs about 1–3 minutes to go
connected → syncing → tracking → full, so 5m avoids paging on every restart.
**Response:** check peers (`PFTNoPeers`/`PFTLowPeers`), `pft_validated_ledger_age_seconds`, disk I/O and clock
(`timedatectl`). If it's stuck in `connected`, check that 2559/tcp is reachable and the `[ips]`/`[ips_fixed]` config.

### PFTValidatorNotProposing
A validator key is loaded (`pft_validator_configured == 1`) and the state is below `proposing` (6) for 10m ·
**critical**. A validator that's configured but not proposing isn't contributing to consensus. The alert is
silent on non-validator nodes.
**Response:** confirm the `[validator_token]` is loaded (`server_info.pubkey_validator`), that the node is `full`,
and that your validator key is on the published UNL / that you've followed the official guide's steps 5–8.

### PFTNoPeers
`pft_peers == 0` for 2m · **critical**. The node is isolated.
**Response:** check outbound connectivity, the firewall (`ufw status`, DOCKER-USER chain) and the `[ips_fixed]`
entries; on a validator behind sentries, check that the sentries are up (see `../sentry`).

### PFTLowPeers
`0 < pft_peers < 5` for 10m · **warning**. A few peers works, but one more disconnect isolates the node. 10m
ignores normal peer churn. Validators behind 1–2 sentries are expected to sit below 5: raise the threshold or
silence it for them.
**Response:** `../peers` diagnostics; check `peers_max` and that inbound 2559 isn't being rate-limited too hard.

### PFTValidatedLedgerOld
`validated_ledger.age > 60s` for 2m · **warning**. Ledgers normally validate every 3–5s, so 60s is more than ten
missed closes. If several nodes fire at once, suspect the network rather than your node.
**Response:** compare with a public node's `server_info`; if only yours is behind, see PFTNodeNotFull.

### PFTValidatedLedgerStalled
`changes(pft_validated_ledger_seq[5m]) == 0` while the RPC answers, for 1m · **critical**. The validated sequence
hasn't moved for 6+ minutes even though the node responds. That's a hard stall (local or network-wide).
**Response:** same as above; check `last_close.proposers` and the `../amendments` status (an amendment blocker
stops validation).

### PFTCompleteLedgersGap
`pft_complete_ledgers_ranges > 1` for 30m · **warning**. `complete_ledgers` like `100-200,250-300` means history
is missing. Short gaps right after a restart are normal while the node backfills, which is why `for` is 30m.
**Response:** confirm it isn't shrinking on its own; check disk space and the `online_delete` setting. A
history-serving node may need a resync of the missing range.

### PFTCloseTimeDrift
`|close_time_offset| > 5s` for 10m · **warning**. `server_info.close_time_offset` only appears when the node's
clock disagrees with network close times. Consensus close times are rounded to a resolution of ≥10s, so 5s
sustained for 10m is real drift, not rounding.
**Response:** `timedatectl`, `chronyc tracking` / `systemctl status systemd-timesyncd`; fix NTP.

### PFTHighLoadFactor
`load_factor > 10` for 10m · **warning**. `load_factor` 1 means unloaded, and the server raises it when it is
overloaded (local fee escalation, slow job queue). A sustained value above 10 means the box is undersized or
something is hammering RPC.
**Response:** check CPU/IO (`top`, `iostat`), the `io_latency_ms` field in `server_info`, and admin RPC callers.
Make sure the RPC ports are still bound to 127.0.0.1 (`sudo postfiat-health`).

### PFTContainerRestarted
`resets(pft_uptime_seconds[15m]) > 0` · **warning**, no `for` (a restart is an event). `server_info.uptime` going
backwards catches container restarts, crashes and `docker compose up -d` recreations. Because it uses
`server_info`, the exporter needs no Docker socket access (it runs `DynamicUser=yes`). The alert resolves 15m
after the restart.
**Response:** if you didn't restart it on purpose, run `sudo docker logs --since 20m postfiatd` and
`journalctl -k | grep -i oom`.

### PFTContainerRestartLoop
`resets(pft_uptime_seconds[1h]) >= 3` · **critical**. Crash loop, OOM kill or a bad config.
**Response:** `sudo docker inspect postfiatd --format '{{.RestartCount}} {{.State.OOMKilled}}'`, then the logs; roll
back the last change (`../upgrade`, `../backup` restore).

### PFTDiskSpaceLow
`avail/size < 15%` for 10m · **warning**. The NuDB/RocksDB store grows continuously, so 15% leaves time to act.
**Response:** `sudo du -sh /var/lib/docker/volumes/*`, prune old images (`docker image prune`), check
`online_delete`, and grow the disk.

### PFTDiskSpaceCritical
`avail/size < 5%` for 5m · **critical** (inhibits PFTDiskSpaceLow). The database fails writes when the disk is
full, and the node falls out of sync.
**Response:** free space immediately (image/log prune), then follow PFTDiskSpaceLow.

### PFTDiskWillFillIn24h
`predict_linear(avail[6h], 24h) < 0` and less than 30% free, for 30m · **warning**. This is the early warning
for fast growth (log explosion, a missing `online_delete`). The 30% guard stops it firing on large, mostly
empty disks during short write bursts.
**Response:** find what's growing (`du`, `docker system df`) and fix it before PFTDiskSpaceLow.

## Tests

```bash
python3 gen_tests.py > tests.yml          # regenerate after editing rules or cases
DOCKER="sudo docker" ./run-stack.sh check
```

`gen_tests.py` exits with an error if any alert in the rules file has no test case. Note that promtool input
series are sampled at `interval`. Lookback is 5m, so long intervals make conditions blink between samples and
reset `for:` timers. Use 1m.

## Proof logs

See [`../logs/alerts/`](../logs/alerts/):

| Log | Contents |
|---|---|
| `1-shellcheck-promtool-stack-up.log` | shellcheck, promtool check/test, first stack start-up with loopback verification |
| `2-promtool-mutation-check.log` | the tests fail when two rules are broken on purpose |
| `3-live-drill.log` | shellcheck, promtool check/test, stack up with ntfy on, then the live drill: postfiatd stopped → `PFTNodeRPCDown` pending → firing/active in Alertmanager → node restored to `full` → all alerts resolved |
| `4-post-drill.log` | full webhook log, including the `PFTContainerRestarted` resolved notification sent after the drill exited; both APIs empty; only 22/2559 listen beyond loopback |

Alertmanager never sees `pending`: Prometheus sends an alert to Alertmanager only after its `for:` has elapsed.
So the drill reads `pending` from the Prometheus `/api/v1/alerts` API, and reads `active`/resolved from the
Alertmanager `/api/v2/alerts` API and its webhook notifications.
